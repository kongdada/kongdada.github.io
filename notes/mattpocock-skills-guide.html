mattpocock/skills 使用文档

mattpocock/skills（MIT License）是一套面向软件工程流程的模块化 Markdown Skill 集合，包含 27 个可独立组合的技能。本文档整理其安装配置、任务路径选择、标准开发工作流、团队落地规范，并附有官方 README 与全部 27 个技能的完整中文翻译。

2026-11-24 AI 工程 Skills

概述与架构

与接管整个仓库的重型 Agent 框架不同，mattpocock/skills 的每个技能均为纯文本 SKILL.md（部分附带脚本或模板），按需加载以控制上下文长度。技能按触发方式分为两层：

层级触发方式代表技能职责
编排层（User-invoked） 开发者输入斜杠命令主动触发 /grill-with-docs、/to-spec、/to-tickets、/implement-spec、/retro 控制需求分析、规划、拆分与复盘阶段边界
纪律层（Model-invoked） Agent 在执行任务时按需自动调用 tdd、prototype、domain-modeling、code-review 约束测试驱动开发、原型验证、领域建模与审查标准

任务路径选择

为避免小改动引入不必要的流程开销，建议按改动复杂度选择对应工作流（参考 re-cinq 指南 与 Joao Queiros 实践评测）：

按改动规模划分的 5 条标准执行路径

标准 6 步开发工作流

面向中大型功能需求的推荐闭环如下：

阶段命令关键动作与产出物
1. 需求澄清 /grill-with-docs 聚焦问题背景（Why）而非预设实现（What），通过多轮问答沉淀 GLOSSARY.md（领域术语）与 ADR（架构决策记录）。存在核心分歧时可要求逐题提问，直至共识稳定。
2. 原型与规则确认 prototype / /to-questionnaire 交互方案不确定时，并行生成 2–3 套一次性可交互原型验证手感（不直接合入生产代码）；业务规则存在盲区时，导出异步确认问卷发送给业务方。
3. 规格说明书 /to-spec 输出结构化 Spec（用户故事、技术方案、Out of Scope 清单）。人工必审 5 项：范围边界、核心行为、排除项、数据迁移、验收标准。
4. 任务拆分 /to-tickets 当工作量超出单次上下文窗口或具备并行条件时拆分 Ticket，显式声明 Blocked by 依赖关系，优先切分前置重构与端到端垂直切片（Tracer Bullet）。
5. 压缩与实现 /compact + /implement-spec 决策落盘后立即压缩上下文，避免超过 150k+ Token 后质量下降。单任务使用 /implement（内置 TDD），多工单任务使用 /implement-spec 并行交付。
6. 审查与复盘 /code-review + /pr + /retro 通过独立子 Agent 分别校验代码规范与 Spec 还原度；/pr 区分可回滚变更与不可逆变更；合并后执行 /retro，将高频问题固化为只减不增的 Lint 规则。

命令适用场景功能说明

团队落地与生产治理

核心原则

团队项目不建议原样引入全部 27 个个人技能，推荐采用「Fork 私有化裁剪 + 前置业务知识库 + 生产安全门禁」模式。

1. 流程收敛与业务知识库前置

参考国内商业团队的长期实践（团队复盘文章），多数团队将主流程收敛为 grill-with-docs → to-spec → to-tickets → implement 四步。针对复杂业务下需求澄清阶段追问过多的问题，建议前置维护 AI Coding 业务知识库（业务流程、仓库职责、代码入口、核心库表），供 Agent 在提问前自动检索，并与 /retro 形成互补（知识库沉淀业务上下文，/retro 改进工程环境）。

2. 私有化裁剪与技术栈规范注入

参考海外工程团队经验（Reddit 工程讨论），团队通常通过 Fork 保留核心主干流程，补充适配内部技术栈（如 Java/Spring 微服务、内部 RPC/ORM 事务及日志规范）的 Model-invoked 纪律技能，并通过 /setup-matt-pocock-skills 接入内部 Jira 与 GitLab。

3. 生产环境三项门禁

  • Stacked PRs 分级审查：禁止一次性合入数千行巨型 PR。拆分为可随时回滚的常规 PR 与涉及数据库迁移、权限策略、核心开关的高风险 PR，后者强制人工评审与 Feature Flag 灰度。
  • Lint 棘轮（Shrink-only Ratchet）：面对历史技术债，不中断业务做全面重构，而是通过自定义静态规则锁定存量上限——新增代码零容忍，既有存量只减不增。
  • 内部版本锁定：Skill 包含 Markdown 指令与辅助脚本，生产团队应先完成安全审计，通过内部仓库锁定版本分发，避免直接拉取未审计的外部自动更新。

4. 7 天低风险试点建议

参考 Joao Queiros 试点方案，建议由 1–2 名骨干成员选取 1 个边界清晰、风险可控的中等需求验证闭环：

  • Day 1：完成单一方式安装与 /setup-matt-pocock-skills 初始化，确定试点需求。
  • Day 2–4：执行 /grill-with-docs 沉淀首批术语表与 ADR，生成 /to-spec 并由技术负责人评审范围与数据迁移方案。
  • Day 5–6：按需拆分 /to-tickets，交付首条带自动化测试的端到端切片，记录编码与返工耗时。
  • Day 7：执行 /code-review 与 /retro，裁剪冗余规则并形成团队 v1 规范。

官方文档中文翻译（README 全文）

以下内容译自官方仓库 mattpocock/skills README.md，保留核心原意、原著引文与全部 27 个技能的源码直达链接，便于中文读者对照学习。

1. 设计哲学：Skills For Real Engineers

这套 Agent Skills 是 Matt Pocock 每天用来做真实软件工程（而非 Vibe Coding）的工具集。

开发真正可维护的应用从来不是一件容易的事。像 GSD、BMAD、Spec-Kit 这类方案试图通过「接管整个研发流程」来提供帮助，但代价是剥夺了开发者的控制权，且一旦流程本身出 Bug 会非常难以排查。

因此，这套 Skills 的设计原则是：小巧、易于修改、可自由组合、不绑定特定大模型，沉淀自数十年的软件工程经验。你可以随意改造它，让它真正成为属于你自己的工作流。

2. 为什么需要这套 Skills：解决 AI 编程四大高频痛点

这套技能库最初是为了解决使用 Claude Code、Codex 等编程 Agent 时最常见的四类失败模式：

痛点 #1：Agent 没按我的真实意图干活

「没有人一开始就知道自己到底想要什么。」—— David Thomas & Andrew Hunt，《程序员修炼之道》（The Pragmatic Programmer）

问题所在：软件开发中最常见的失败源于「认知错位」。你以为对方懂了你的需求，结果看到成品才发现它完全理解偏了。AI 时代同样如此，你和 Agent 之间天然存在沟通鸿沟。

解法：在动手写代码之前进行一次深度追问（Grilling Session），让 Agent 就你要做的东西连续抛出细节问题，直到设计树上的每个分支都达成一致：

  • /grill-me：适用于非代码类方案与设计讨论；
  • /grill-with-docs：在 /grill-me 的基础上结合项目文档，顺带打磨领域模型与 ADR。

痛点 #2：Agent 表达过于啰嗦

「有了通用语言，开发者之间的对话与代码中的表达就都源自同一个领域模型。」—— Eric Evans，《领域驱动设计》（Domain-Driven Design）

问题所在：Agent 被空投进一个陌生代码库时，只能边猜边理解业务黑话，于是经常用 20 个词去解释一个本可以用 1 个术语说清的概念。

解法：在仓库中沉淀一份共享术语表（GLOSSARY.md）。以 Matt 的 course-video-manager 项目为例，引入术语表前后的沟通精简程度对比如下：

  • 引入前：「当课程某个章节里的一节课变成『真实存在』（也就是在文件系统里分到了一个位置）时，这里会出现一个问题。」
  • 引入后：「物化级联（materialization cascade）这里出了问题。」
共享语言（GLOSSARY.md）的三个额外收益

① 变量、函数与文件命名高度一致，全部对齐同一套领域词汇；② 代码库对 Agent 更易导航；③ 更精炼的词汇让 Agent 在思考阶段消耗更少的 Token。这一机制已内置在 /grill-with-docs 中，同时会把难以口头解释的权衡写入 ADR。

痛点 #3：生成的代码跑不通

「始终走小而克制的步伐。反馈速度决定了你的研发上限，永远不要一次接过大的任务。」—— David Thomas & Andrew Hunt，《程序员修炼之道》

问题所在：即便你和 Agent 已经对齐了需求，它依然可能写出跑不通的烂代码。此时必须检查你的反馈闭环——如果 Agent 看不到代码运行后的真实结果，它就是在盲飞。

解法：配齐静态类型检查、浏览器访问能力与自动化测试。在自动化测试中，红 → 绿 → 重构（Red-Green-Refactor）循环尤为关键（先写一个失败测试，再实现代码让测试通过）：

  • /tdd：可插入任意项目，引导红-绿-重构循环并明确好测试与坏测试的标准；
  • /diagnosing-bugs：将排障最佳实践封装成按阶段设门禁的诊断闭环。

痛点 #4：代码库迅速腐化成「大泥球（Ball of Mud）」

「每天都持续投入精力打磨系统设计。」—— Kent Beck，《解析极限编程》（Extreme Programming Explained）
「最好的模块是深模块：通过极简的接口，向外提供丰富的能力。」—— John Ousterhout，《软件设计哲学》（A Philosophy of Software Design）

问题所在：Agent 极大提升了写代码的速度，也同样加速了软件熵增——代码库正以前所未有的速度变得复杂、难以修改。

解法：在 AI 时代依然坚持重视代码设计。/to-spec 会在生成规格前先盘问涉及哪些模块；更重要的是每隔几天运行一次 /improve-codebase-architecture，扫描代码库中可以「做深模块」的重构候选点（注意：它是架构巡检工具，而非老烂尾项目的急救魔法）。

官方小结：软件工程基本功比以往任何时候都更重要。这套 Skills 的目标，就是把这些基本功浓缩成可重复执行的工程实践。

3. 官方全量 27 个技能参考手册（中英对照）

官方按调用权限将全部技能划分为两类：User-invoked（用户触发）仅在你主动输入命令（如 /grill-me）时运行，负责流程编排；Model-invoked（模型触发）既可由你手动调用，也可由 Agent 在匹配场景下自动启用，负责封装可复用的工程纪律。约束规则：用户触发技能可以调用模型触发技能，但绝不会调用另一个用户触发技能。

Engineering · 工程类技能（20 个，日常写代码高频使用）

技能名称（直达源码）触发方式官方功能说明（中文译注）
ask-mattUser-invoked询问当前场景适合哪个技能或流程，作为本仓库所有用户触发技能的路由器。
grill-with-docsUser-invoked在深度追问对齐需求的同时构建项目领域模型，打磨术语并直接更新 GLOSSARY.md 与 ADR。
triageUser-invoked按分拣角色状态机推进和流转团队的 Issue 工单。
improve-codebase-architectureUser-invoked扫描代码库中适合深化模块的机会，输出可视化 HTML 报告，并对选中的重构项展开深度追问。
setup-matt-pocock-skillsUser-invoked为当前仓库初始化工程技能配置（工单系统、Triage 标签、领域文档路径）。每个仓库使用前运行一次。
to-specUser-invoked将当前对话直接汇总成规格说明书（Spec）并发布到工单系统；不再追问，仅提炼已达成共识的内容。
to-ticketsUser-invoked将计划、Spec 或对话拆分为一组带阻塞依赖关系的端到端切片（Tracer-bullet）工单，支持本地文本或工单系统原生依赖链接。
implementUser-invoked按 Spec 或工单集合完成编码实现，在约定边界处驱动 /tdd，并在提交前执行 /code-review 收口。
implement-specUser-invoked在单条集成分支上实现整份 Spec：将工单按任务图编排，并行派生实现子 Agent 推进就绪任务，最终以 /code-review 收口。
wayfinderUser-invoked针对超出单次会话容量的超大型项目，在工单系统上建立共享的「决策工单地图」，逐个消解不确定性直至路径清晰。
retroUser-invoked会话结束后复盘并按严重程度优先提出 Agent 工程环境改进建议（目录导航、自动检查、编码规范、引导文件与工具链）。
prototypeModel-invoked快速构建一次性原型来回答设计问题：状态/逻辑验证生成单个可分享 HTML，UI 探索则在同一路由下生成多套风格迥异的可切换方案。
diagnosing-bugsModel-invoked针对疑难 Bug 与性能回退的严谨排查闭环：构建红灯复现 → 最小化 → 提出假设 → 插桩验证 → 修复 → 回归测试。
researchModel-invoked以后台子 Agent 方式基于高可信一手资料调研技术问题，并在仓库内沉淀带引用的 Markdown 研究文档。
tddModel-invoked遵循红-绿-重构循环的测试驱动开发，每次聚焦一个垂直切片完成功能或修复缺陷。
domain-modelingModel-invoked主动构建并打磨项目领域模型：对照术语表质疑不准确命名、用边界场景压力测试，并即时更新 GLOSSARY.md 与 ADR。
codebase-designModel-invoked设计「深模块」的共享工程纪律与词汇：将复杂行为收敛在极简接口之后，切分清晰接缝，并确保可通过接口直接测试。
code-reviewModel-invoked对固定基线以来的代码变更做双轴并行审查：Standards（是否符合仓库规范及 Fowler 代码坏味道基线）与 Spec（是否忠实实现原需求），由两个独立子 Agent 执行避免互相干扰。
prModel-invoked规范 Pull Request 描述结构：用最精简的可视化方式说明改动、提供改前/改后有效证据，并明确标注合并风险（单向门/双向门及影响半径）。
wizardModel-invoked生成交互式 Bash 向导脚本，分步引导人类完成只有人工能做的操作（开通云资源、配置凭据或 CI 密钥、操作陌生第三方后台、一次性数据迁移或切流）。
