mattpocock/skills 实战指南：从安装配置、全流程上手到企业级团队落地

mattpocock/skills（MIT 开源，33 万+ Star）不是接管一切的黑盒框架，而是 27 个小而美、可自由组合的工程 Markdown Skill。上手它不需要背完 27 条命令——个人开发只需跑通「1 次初始化 + 6 步主流程」，企业落地则聚焦于「知识库前置 + 私有化裁剪 + 生产安全门禁」。

2026-11-24 支持：Claude Code / Codex / Copilot / Gemini CLI / Cursor

STEP 030 秒安装与仓库初始化

02核心主流程：单需求 6 步实操

STEP 01/grill-with-docs

只讲 Why 不讲 What。通过多轮追问沉淀 GLOSSARY.md（统一术语）与 ADR（记录权衡）。遇到核心分歧时要求「一次只问一个问题」；连续回复「同意」即对齐完成。

STEP 02prototype / /to-questionnaire

交互拿不准，派子 Agent 一次做 2–3 版一次性原型（切忌照搬进生产）；碰到产品经理没定的规则盲区，用 /to-questionnaire 一键生成异步问卷发给业务方。

STEP 03/to-spec

将共识合成为施工蓝图（用户故事、实现决策、明确的 Out of Scope）。人工必审 5 项：范围边界、核心行为、排除项、数据迁移、验收标准。

STEP 04/to-tickets

仅当任务超单次上下文或可并行时拆分。每张 Ticket 声明依赖关系（Blocked by），优先切出前置重构与端到端垂直切片（Tracer Bullet）。

STEP 05/compact + /implement-spec

决策落盘后立即压缩上下文，避开 150k+ Token 愚蠢区。小功能用 /implement（含 TDD），多工单大需求用 /implement-spec 离席并行交付。

STEP 06/code-review + /pr + /retro

双独立子 Agent 分别审查「规范」与「Spec 还原度」；/pr 标注双向门/单向门风险；合并后跑 /retro 把 Review 痛点沉淀为只减不增的 Lint 棘轮。

04企业级项目落地参考

核心判断：企业团队不要照搬全套 27 个个人技能

多人并行开发时，个人向的上下文技能容易冲突。正确姿势是 Fork 私有化裁剪 + 前置业务知识库 + 生产安全门禁。

1. 国内商业团队实战：四步流水线 + AI Coding 业务知识库

据歪歪在 团队数月实践复盘 中的经验：团队收敛为 grill-with-docs → to-spec → to-tickets → implement 四步，统一全员话术并落地「重设计、轻编码」。针对复杂业务下 AI 追问 79 个问题导致开发者「力竭」的痛点，团队自建 AI Coding 业务知识库（业务流程、仓库边界、代码入口、库表设计）供拷问前先查库。待攻克课题是「合并主干时自动触发知识库增量更新」，与 /retro 形成互补（知识库补业务背景，/retro 优化工程环境）。

2. 海外多人团队实践：Fork 裁剪 + 注入公司技术栈纪律

在 Reddit 工程团队讨论 中，团队选择 Fork 后仅保留主干工作流，并为公司常用技术栈（如 Java/Spring 微服务、内部 RPC/ORM 事务与日志规范）编写专属的 Model-invoked 纪律 Skill，同时通过 /setup-matt-pocock-skills 对接 Jira / GitLab。

3. 生产环境三大硬门禁

  • Stacked PRs 分级审查：绝不一次性合入数千行巨型 PR。拆成可随时回滚的双向门小 PR，对数据库迁移、权限与核心开关等单向门强制人工严审 + Feature Flag 灰度（参见 Matt 实战视频）。
  • Lint 棘轮（Shrink-only Ratchet）：老项目历史债务多，不搞停工大重构，直接上线自定义静态规则锁死存量上限——新代码零容忍，旧存量只减不增。
  • 内部版本锁定：Skill 为纯文本 Markdown 与脚本，企业应先做安全审计并通过内部仓库分发锁定版本，不直接拉取未审外部更新。

05可直接照抄的 7 天低风险试点路线

参考 Joao Queiros 试点方案，先选 1–2 名业务骨干 + 1 个有真实模糊度但风险可控的中等需求跑通闭环：

DAY 01
建仓与选点
单选方式安装，跑通 /setup-matt-pocock-skills，选定边界清晰的中等试点需求。
DAY 02–04
拷问与严审蓝图
跑 /grill-with-docs 沉淀首批术语与 ADR；跑 /to-spec 由技术负责人严审范围与迁移风险。
DAY 05–06
切片交付测返工
按需 /to-tickets，先交付 1 条带自动化测试的垂直切片，量化记录编码与返工耗时。
DAY 07
双轴复盘与裁剪
执行 /code-review 与 /retro，删掉无效指令，固化为团队 v1 规范后再推广。
